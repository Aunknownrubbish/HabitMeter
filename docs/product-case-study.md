# HabitMeter / 寻栖 产品案例

## 1. 产品背景

租房或选择居住地时，用户通常需要同时判断多个问题：通勤多久、附近有没有地铁和公交、生活便利度如何、附近是否有医院和公园、多个候选房源到底哪个更适合自己。

这些信息本身并不难获得，但它们分散在地图、租房平台、聊天记录、截图和个人笔记里。用户最终很容易陷入两种状态：

- 看了很多信息，但没有形成明确判断。
- 记住了单个房源的优点，却很难横向比较多个候选。

HabitMeter 的核心切入点是：把地址周边数据和通勤数据整理成一个可比较、可复述、可决策的居住结论。

## 2. 目标用户

当前版本主要面向需要在城市中选择居住地点的人群：

- 正在租房、看房、换房的人。
- 需要在居住成本、通勤时间、生活便利之间做取舍的人。
- 同时比较多个候选小区、房源或区域的人。
- 对一个城市不够熟悉，需要快速判断某个地址生活条件的人。

## 3. 核心问题

### 信息碎片化

用户通常需要在多个工具之间切换：地图查地址、导航查通勤、搜索周边设施、用表格或备忘录记录候选。每个工具都只回答局部问题。

### 判断标准不统一

一个地址“看起来不错”，可能只是因为交通强；另一个地址生活便利，但通勤压力大。如果没有统一维度，用户很难把不同候选放在同一个判断框架里。

### 多候选比较困难

租房决策很少只看一个地址。真实场景往往是 3 到 6 个候选反复比较：今天觉得 A 好，明天看到 B，又忘了 A 的短板。这个过程需要结构化记录和对比。

## 4. 产品目标

HabitMeter 的目标不是替用户做最终选择，而是降低判断成本。

产品希望完成三件事：

1. 把一个地址转化为清晰的居住环境结论。
2. 把通勤、交通、生活、医疗、休闲放入同一个评分框架。
3. 把多个候选地址变成可以排序、比较和讨论的清单。

## 5. MVP 范围

v1.0.0 的 MVP 目标是验证基础链路能否跑通：

- 输入候选居住地，即地址 A。
- 在地图上定位地址 A。
- 搜索 3km 范围内的 POI。
- 输入通勤目的地，即地址 B。
- 获取驾车、公共交通、步行、骑行四种通勤方案。
- 登录后收藏地址。

这个阶段的重点是“数据能否拿到”和“流程能否成立”，还没有强调产品判断力。

## 6. P0 为什么先做

P0 阶段没有急着加新功能，而是先修稳定性、安全和错误状态。这是因为居住决策工具的信任感建立在稳定反馈上：

- 如果路线请求失败却一直 loading，用户会以为产品不可用。
- 如果地图加载失败没有提示，用户不知道问题来自网络、配置还是产品本身。
- 如果密钥暴露在前端，项目不适合公开展示。
- 如果 TypeScript build 不稳定，后续迭代会越来越难控。

P0 的产品意义是：让工具从“本地能跑”变成“别人也能相对可靠地打开和理解”。

## 7. P1 为什么做

P1 的核心目标是从“展示信息”升级为“给出判断”。

MVP 能告诉用户附近有什么、通勤多久，但还不能直接回答“这个地方适不适合住”。因此 P1 增加了：

- 居住评分模型。
- 结论摘要卡。
- POI 可达性评价。
- 通勤推荐。
- 更符合决策顺序的信息架构。

这一步让产品的价值从数据罗列变成了决策辅助。用户看到的第一层信息不再是 POI 列表，而是总分、等级、优势和短板。

## 8. P2 为什么做

真实租房决策通常不是单地址判断，而是多候选比较。

P2 的目标是把 HabitMeter 从“分析一个地址”推进到“辅助一轮选择”。因此新增：

- 候选清单。
- 多候选横向对比。
- 维度优胜判断。
- 偏好模式排序。
- 复制对比报告。

这一步的关键变化是：用户可以把多个地址留在同一个决策空间里，而不是每次重新搜索、重新记忆、重新比较。

## 9. 关键产品设计决策

### 为什么使用 A/B 地址

地址 A 是候选居住地，地址 B 是通勤目的地。这个结构足够简单，也贴近真实决策。

如果只分析 A，产品只能评价生活圈；加入 B 后，产品才能判断居住地和日常目的地之间的关系。对城市居住决策来说，通勤通常是最高权重因素之一。

### 为什么使用 3km 生活圈

3km 是一个偏实用的生活半径：

- 对便利店、公交站、地铁站等高频设施，3km 足以覆盖主要选择空间。
- 对公园、医院等低频但重要设施，3km 能提供基本安全感判断。
- 范围太小会漏掉重要配套，范围太大会稀释“日常可达”的意义。

当前版本还会在 POI 搜索后做精确距离过滤，确保列表和地图标记只保留 3km 内结果。

### 为什么需要评分模型

评分模型的目的不是追求绝对客观，而是提供稳定的比较框架。

当前模型分为五个维度：

- 通勤
- 交通
- 生活
- 医疗
- 休闲

用户可以不完全相信总分，但可以通过维度拆解理解“为什么这个地址被推荐或不推荐”。这比只给一个结论更透明。

### 为什么需要偏好模式

不同用户的权重不一样。有人宁愿住远一点但生活便利，有人只关心通勤，有人更关注医院、公园或公共交通。

因此 P2 没有修改原始评分模型，而是在候选对比里增加偏好加权排序：

- 原始综合分仍然保留。
- 偏好分只影响候选对比排序。
- 切换偏好模式后，最佳候选和排名会更新。

这样既保留了统一基准，也允许用户表达场景差异。

### 为什么候选清单先用 localStorage

候选对比是一个轻量、高频、个人化的功能。当前阶段用 localStorage 有三个好处：

- 不需要登录也能使用。
- 不改数据库 schema，降低实现风险。
- 适合作为本地演示和个人决策工具。

它的限制也很明确：换设备或清除缓存后会丢失。服务端同步可以放到后续 P3。

## 10. 当前版本能力边界

当前版本适合用于：

- 单个地址居住环境分析。
- A/B 地址通勤判断。
- 多候选本地比较。
- 轻量级演示和产品案例展示。

当前版本不适合承诺为完整生产级能力：

- 候选清单尚未账号同步。
- SQLite 不适合多实例线上部署。
- 路线结果还没有绘制到地图上。
- 评分模型还没有经过真实用户数据校准。

## 11. 后续规划

### P3：正式产品化基础

- 候选清单服务端同步。
- 数据库从 SQLite 迁移到 PostgreSQL / Supabase / Neon。
- 路线 polyline 可视化。
- 候选快照持久化和刷新机制。

### P4：决策体验增强

- 候选报告导出。
- 更细的用户偏好设置。
- 房租、预算、面积等非地图因素录入。
- 候选地址标签和筛选。

### P5：模型与数据校准

- 根据用户反馈调整评分权重。
- 增加城市差异配置。
- 引入更多设施类型和负面因素，如噪音、学校、商圈密度等。

## 12. 项目总结

HabitMeter 的阶段性价值在于，它把一个模糊的生活选择问题拆成了可计算、可展示、可比较的产品流程。

从 MVP 到 P0/P1/P2，项目的演进路径是：

- 先跑通核心数据链路。
- 再补稳定性和安全边界。
- 再从数据展示升级到结论判断。
- 最后扩展到多候选比较。

这条路径让产品从一个地图工具，逐步变成一个居住决策辅助工具。
